# CORS and public MCP endpoints - 2026-11-02

Guidon task `912c9711` ([ZAP P1] Audyt CORS i publicznych endpointów MCP),
related to the API/MCP authorization QA task `f76a9572`.

ZAP reported `Access-Control-Allow-Origin: *` on the MCP server cards,
`/auth.md`, `robots.txt` and `sitemap.xml`. The production responses were
checked with a foreign `Origin`, with and without a session cookie, and with
an `OPTIONS` preflight asking for `Authorization`.

## Result

No change to the headers. The wildcard is only on documents that are the
same for every visitor, and nothing in the app allows credentials cross-origin:

- **No response sends `Access-Control-Allow-Credentials`.** With `*`,
  browsers refuse to expose a credentialed response, so another site can
  never read anything with the visitor's session.
- **Signed-in routes send no CORS headers at all** (`/api/v1/*`, `/api/mcp`,
  `/api/ai/*`, pages). Another site can't read them, even when the browser
  carries a live session.
- **Session cookies are `SameSite=Lax`** (`guidon-session`; Supabase's own
  cookies are Lax too), so a cross-site form POST doesn't carry the session.
  The cookie-authenticated POST routes (`/api/ai/chat`) can't be driven
  from another site.

## Decisions per endpoint

| Endpoint | CORS | Why |
|---|---|---|
| `/api/mcp/server-card`, `/api/mcp/docs/server-card` | `*`, GET/HEAD | Public description of the MCP servers (name, URL, auth method). Same for everyone, no data. Browser-based MCP clients read it. |
| `/auth.md`, `/openapi.json`, `/llms.txt`, `robots.txt`, `sitemap.xml` | `*` | Public documentation and crawl files. `robots.txt`/`sitemap.xml` get the wildcard from the platform's static file handling. |
| `/.well-known/*` (OAuth metadata, JWKS, API catalog, agent card, key directories) | `*` | RFC 8414/9728 metadata and public keys. Browser-based OAuth clients must read them. |
| `/oauth/token`, `/oauth/register`, `/oauth/revoke` | `*`, POST | OAuth 2.1 public clients (PKCE, no secret) run in browsers. Credentials are the code/refresh token in the body, never cookies. |
| `/api/v1/projects/{id}/reports` | `*`, POST | In-game reports from browser games, authenticated by a bearer key that can only file reports. No cookies. |
| `/ask` | `*`, GET/POST | NLWeb search over public documentation only. No user data. |
| `/api/v1/*`, `/api/mcp`, `/api/mcp/docs` | none | Bearer-key or OAuth clients are servers, not browsers on another site. Some `/api/v1` reads also accept the session for the app's own search, so they must stay same-origin. |
| `/api/ai/*`, pages, Server Actions | none | Session only, same-origin. |

## Tests

`tests/e2e/smoke.mjs`, while signed in:

- the public documents answer a foreign `Origin` with `*` and never with credentials;
- `GET /api/v1/search`, `GET /api/v1/projects`, `POST /api/mcp`, `POST /api/ai/chat` and `OPTIONS` preflights on `/api/v1/projects` and `/api/mcp` answer a foreign `Origin` with no `Access-Control-Allow-Origin` and no credentials;
- the session cookie isn't `SameSite=None`.

## When to revisit

A new route that adds `Access-Control-Allow-Origin` must not read the
session cookie, and must never add `Access-Control-Allow-Credentials` or
echo the request's `Origin`. If the browser app ever calls the API from
another origin (for example a separate app domain), use an allowlist of
exact origins with credentials, not a wildcard.
