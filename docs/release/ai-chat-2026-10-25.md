# AI chat release QA — 2026-10-25

Continuation after PR #72 merged (`17ae426`). Board card:
`3be4feeb-795e-491d-8909-3156cb99be52`.

## Changes

The project chat previously passed raw provider error messages into its HTTP
response and logged the complete exception. Provider exceptions could contain
response bodies. Its entry point also lacked the project's AI-disabled gate,
write-role gate and bounded message validation used by the task assistant.

The chat now requires a signed-in owner/admin/developer with access to an
AI-enabled project before resolving a provider or charging its request counter.
The project layout shows the chat only to those callers. Existing Server Action
and database authorization still own each tool mutation; the request project
and actor are supplied by the server, not by model-generated arguments.

Incoming history allows only user/assistant text, at most 20 messages with
8000 characters each, ending with a non-empty user message. The browser sends
the latest 20 messages. System/tool impersonation is rejected. Retrieved tool
content remains a tool message and is explicitly described as untrusted data.
This is defense in depth, not proof that a model can never follow an injection.

Each turn has a 120-second deadline, at most five model completions with
1000 output tokens per completion, and at most 20 tool calls across the turn.
Unknown or excessive calls are rejected before their dispatch. Existing
20-messages-per-five-minutes per-user/project throttling remains in place.
This counter remains process-local: it is not a shared financial quota or a
strict organization-wide spending cap.

All provider transports combine optional caller cancellation with their
existing request timeout. The chat checks cancellation before another model or
tool operation. The browser can stop a request and also aborts on close/unmount.
An in-flight database mutation can finish, and already completed changes remain
saved; cancellation is not a transaction rollback. The UI explains this and
advises refreshing the board before retrying. There is no automatic retry of
a partially executed turn.

Provider HTTP exceptions retain status codes without their response bodies.
Chat errors use controlled timeout/rate-limit/unavailable codes and log only
the code. Provider resolution is inside the same error boundary. The separate
task-planning chat also uses the safe provider failure message.

## Validation and limits

`npm run test:ai` includes the existing 57 provider/factory, 15 task-learning
and 56 module-builder transport cases, plus the actual chat HTTP handler with
63 failure/cancellation cases over seven real provider adapters. Fetch is
replaced: no external network, real credentials or billed tokens are used.
Authentication, provider resolution, workflow reads and tool dispatch are
explicit test boundaries; this suite is not a live-database tool integration.

The handler suite covers 401/429/500 from providers, malformed/empty output,
timeout/abort, configuration-error redaction, permission/AI-disabled gates,
invalid history, safe logs, valid replies, server-owned project binding,
untrusted retrieved text, unknown tools, aggregate tool budget and cancellation
between tools. It exercises the actual request counter: 20 allowed messages,
the 21st denied before provider execution, and separate user/project keys.
Tests verify that failures before dispatch perform no tool calls.

The clean production-browser suite additionally exercises real cookie sessions,
anonymous/viewer/foreign-project denial, the AI-disabled switch, absent-provider
behavior and hiding unavailable chat controls. Browser tests stop a pending
request, observe the cancellation message and successfully send another request.
These use an intercepted response only for the browser stop/recovery behavior;
the actual provider cancellation path is tested separately above.

Guidon's MCP server dispatches tools to `/api/v1`; the model/provider runs in
the external MCP client. Existing 110 real REST/MCP authorization/isolation regression checks are
retained. These tests do not certify every external agent/model against prompt
injection or cover a model's private cancellation/billing behavior.

Final clean-production-build run `5bbc9388f109` passed in Chromium, Firefox
and WebKit, including the production HTTP gates, browser stop/recovery, all
existing release regressions and 110 REST/MCP checks. All 27 axe scans report
zero violations; four incomplete checks per browser still need manual review.
TypeScript, focused ESLint and `test:ai` passed. Traces, videos and JSON evidence
are local under `output/e2e/5bbc9388f109/` and are not committed.

Two failed exploratory runs are not counted as passes. They exposed test
lifecycle issues: clearing cookies while sidebar prefetches were active, and
clicking a task before an explicitly requested document reload committed in
WebKit. Tests now leave the authenticated tree before clearing its session and
wait for the main-frame navigation before opening the reloaded task. No longer
timeouts, forced clicks or disabled guards were introduced.

No new migration, production configuration change, deployment or real payment
is part of this batch. Cloud and multi-replica financial quota validation remain
separate gates.
