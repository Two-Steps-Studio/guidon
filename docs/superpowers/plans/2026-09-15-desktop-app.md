# Guidon Desktop (Tauri, Windows) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Windows desktop app (`desktop/`, a Tauri 2 project) that opens a native window pointed at a configurable Guidon URL (default `https://useguidon.com`), with a system tray icon, close-to-tray behavior, optional autostart, and auto-update wired to GitHub Releases. No changes to the Next.js app itself.

**Architecture:** Tauri's own scaffolding tool (`npm create tauri-app@latest`) generates the baseline project; each task then adds one capability via Tauri's official plugin system (`cargo tauri add <plugin>`) plus targeted edits to the generated Rust/config files. This plan gives you the exact commands to run and the exact behavior to verify at each step, but — unlike the rest of this codebase's TypeScript plans — does **not** hand-write Rust source from scratch, since Tauri 2's exact generated file shape depends on the CLI version installed at scaffold time. Read what the CLI actually generates and Tauri's own docs (`https://tauri.app/`) rather than assuming a specific API surface from memory; if what you find contradicts something this plan assumes, trust what's actually there and note the discrepancy in your report.

**Tech Stack:** Tauri 2 (Rust + a native WebView2 window on Windows), no separate frontend framework for the shell itself — the two local UI surfaces this project owns (the settings window) are plain HTML/JS, not React, since they're small and don't need Next.js's tooling.

### Task 0: Toolchain check (read first, do not skip)

Before Task 1, confirm the machine has what Tauri needs. This was already checked once during planning and found present, but re-verify since environments drift:

- [ ] **Rust toolchain**: run `rustc --version` and `cargo --version`. If either is missing, install via `https://rustup.rs` (downloads and runs `rustup-init.exe`) — this is a system-level toolchain install, not an npm package; if you're an agent and system-level installs are outside what you're allowed to run non-interactively, STOP and report NEEDS_CONTEXT rather than attempting a silent workaround.
- [ ] **MSVC C++ build tools**: run `"C:\Program Files (x86)\Microsoft Visual Studio\Installer\vswhere.exe" -latest -products "*" -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 -property installationPath` — should print an install path (already confirmed present on this machine as of planning time: Visual Studio 2022/18 Community). If empty, Rust's default MSVC target can't link on Windows; this needs the "Desktop development with C++" workload installed via the Visual Studio Installer, which is also a system-level, human-attended install — escalate rather than attempting it silently.
- [ ] **WebView2 runtime**: already confirmed present on this machine (ships with Windows 10/11 by default; `reg query "HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}"` returns a version if so).

If all three are present, proceed to Task 1. Report BLOCKED with specifics if any is missing and you can't install it yourself.

### Task 1: Scaffold the Tauri project, point it at Guidon, verify it builds and runs

**Files:**
- Create: `desktop/` (entire Tauri project, generated by the CLI)

- [ ] **Step 1: Scaffold**

From the repo root:
```bash
npm create tauri-app@latest desktop -- --template vanilla --manager npm
```
When prompted (or via flags, check `npm create tauri-app@latest -- --help` for non-interactive flags): app name `Guidon Desktop`, identifier `com.guidon.desktop`, template "Vanilla" (plain HTML/JS — we are not building a React frontend here, the shell has almost no UI of its own). This generates `desktop/src-tauri/` (the Rust project) and `desktop/src/` (a placeholder local frontend — you'll replace this in Task 2, ignore its default content for now).

- [ ] **Step 2: Point the main window at Guidon instead of the local placeholder**

Tauri 2 supports a window loading a remote URL directly. In `desktop/src-tauri/tauri.conf.json`, find the `app.windows` array's entry and change its `url` (or equivalent field — check the actual generated key name, it may be under a different path depending on the installed CLI version) from the local `index.html` to `"https://useguidon.com"`.

This alone is enough to prove the core concept. Do NOT yet add any capability/permission grants for this window beyond Tauri's default (which grants none) — per the spec, remote content gets zero native API access in this app, by design, for the whole project.

- [ ] **Step 3: Build and smoke-test**

```bash
cd desktop
npm install
npm run tauri dev
```
Expected: a native window opens showing the real Guidon Cloud landing page (dark background, "GUIDON" wordmark, hero text) — confirms the WebView2 remote-URL loading works end-to-end. Close the window, confirm the process exits (no tray yet — that's Task 3).

Then:
```bash
npm run tauri build
```
Expected: produces a Windows installer (`.msi` and/or `.exe` under `desktop/src-tauri/target/release/bundle/`) with no errors. This build will take longer than the dev run (several minutes) — that's normal for a first Rust build (subsequent builds are incremental and much faster).

- [ ] **Step 4: `.gitignore`**

Add `desktop/src-tauri/target/` and `desktop/node_modules/` to the repo's root `.gitignore` if the scaffolding tool didn't already create a `desktop/.gitignore` covering them (check first — it usually does; if `desktop/.gitignore` exists and covers this, don't duplicate it in the root one).

- [ ] **Step 5: Commit**

```bash
git add desktop/ .gitignore
git commit -m "Scaffold Tauri desktop shell pointed at Guidon Cloud"
```

(Do not commit `desktop/src-tauri/target/` or `desktop/node_modules/` — verify `git status` shows neither staged before committing.)

### Task 2: Local settings window (server URL + config persistence)

**Files:**
- Modify: `desktop/src/` (replace the scaffolded placeholder with a real settings page)
- Modify: `desktop/src-tauri/tauri.conf.json` (add a second window definition for Settings)
- Modify: `desktop/src-tauri/src/` (wire up the config-read/write and window-navigate logic)
- Add plugin: Tauri's Store plugin for persisted local config (`cargo tauri add store` from `desktop/src-tauri/`)

- [ ] **Step 1: Add the Store plugin**

From `desktop/src-tauri/`:
```bash
cargo tauri add store
```
This adds the dependency and wires its `init()` call into the generated `main.rs`/`lib.rs` automatically — read what it actually changed (`git diff`) rather than assuming.

- [ ] **Step 2: Build the local settings page**

Replace `desktop/src/index.html` (or add a new `desktop/src/settings.html` — your call based on what reads cleaner given the scaffolded structure) with a minimal form: one text input for the server URL (pre-filled from the stored config, defaulting to `https://useguidon.com` if unset), a "Save & Reload" button. On submit: validate it's a plausible URL (starts with `http://` or `https://`), write it to the Store plugin's persisted store, then trigger the main window to navigate to the new URL (Tauri's window API can `eval`/navigate another window from this context — check the Store plugin's and window API's actual current method names in the generated project/Tauri docs rather than guessing).

- [ ] **Step 3: Wire a way to open Settings from the main window**

Since the main window shows remote, zero-API-access content, the Settings window can't be opened by a button inside the Guidon web page. Add a native menu item instead (Tauri's `Menu`/`MenuItem` API, generated scaffolding usually includes a basic menu already) — e.g. a "Guidon Desktop" or "File" menu with a "Settings..." item that opens/focuses the settings window.

- [ ] **Step 4: On startup, load whatever URL is currently stored**

The main window's initial URL should come from the Store plugin's persisted value (falling back to `https://useguidon.com` if never set), not the hardcoded value from Task 1. This likely means moving the "what URL does the main window load" decision from static `tauri.conf.json` into Rust code that runs at startup (read the store, then create/navigate the main window) — check Tauri's docs for the current recommended pattern (a `setup()` hook is the usual place).

- [ ] **Step 5: Verify**

`npm run tauri dev` from `desktop/`: confirm the app opens Guidon Cloud by default, open Settings via the menu, change the URL to `http://localhost:2137` (with the actual Next.js dev server running via `npm run dev` from the repo root in another terminal), Save & Reload, confirm the main window now shows the local dev server's login page. Quit and relaunch the app (`npm run tauri dev` again) — confirm it now defaults to `http://localhost:2137` (persistence across restarts).

- [ ] **Step 6: Commit**

```bash
git add desktop/
git commit -m "Add a local settings window for choosing the Guidon server URL"
```

### Task 3: Tray icon, close-to-tray, Quit

**Files:**
- Modify: `desktop/src-tauri/tauri.conf.json` (tray icon config)
- Modify: `desktop/src-tauri/src/` (tray menu, window close-event interception)
- Add an icon asset under `desktop/src-tauri/icons/` if a suitable tray-specific one doesn't already exist from scaffolding (the default scaffolded app icon is usually fine to reuse for the tray too — don't design a new one unless the existing one looks wrong at tray size, 16x16/32x32).

- [ ] **Step 1: Add tray icon + menu**

Tauri 2's tray API (`tauri::tray::TrayIconBuilder` or the current equivalent — check docs/generated scaffolding for the exact current shape) with a menu: "Show/Hide Guidon", "Quit". Wire the tray icon's own click (not a menu item) to toggle the main window's visibility.

- [ ] **Step 2: Intercept the main window's close (X button)**

By default, clicking the window's close button quits the whole app. Change this: intercept the `CloseRequested` event on the main window, call `.prevent_default()` (or the current API's equivalent), and hide the window instead. Only the tray menu's "Quit" item should actually call the real exit (`app.exit(0)` or equivalent).

- [ ] **Step 3: Verify**

`npm run tauri dev`: confirm a tray icon appears in the Windows system tray. Click the main window's X button — confirm the window disappears but the tray icon remains (process still running, check Task Manager). Click the tray icon — confirm the window reappears. Right-click the tray icon, click "Quit" — confirm the process actually exits (check Task Manager again).

### Task 5: Auto-update wiring

**Files:**
- Modify: `desktop/src-tauri/tauri.conf.json` (updater plugin config, manifest URL)
- Modify: `desktop/src-tauri/src/` (check-for-update call, e.g. on startup or from a menu item)
- Create: signing keypair for update artifacts (Tauri's updater requires this — `cargo tauri signer generate`)

- [ ] **Step 1: Add the plugin and generate a signing keypair**

From `desktop/src-tauri/`:
```bash
cargo tauri add updater
cargo tauri signer generate -w ~/.tauri/guidon-desktop.key
```
This produces a private key (keep it out of the repo — store the path/passphrase somewhere the user controls, NOT committed) and a public key. Put the **public** key into `tauri.conf.json`'s updater config (`plugins.updater.pubkey` or the current equivalent field). The private key signs release builds later, at release time — not something this task needs to actually run against a real release.

- [ ] **Step 2: Point the updater at a GitHub Releases manifest URL**

`tauri.conf.json`'s updater config takes an `endpoints` array — a URL template pointing at where `latest.json` will live once releases are published, typically `https://github.com/<org>/<repo>/releases/latest/download/latest.json` for a Tauri project releasing via GitHub Releases (confirm this exact URL shape against current Tauri docs rather than assuming — the plan's job here is "wire the mechanism correctly," not "guarantee a URL string from memory is byte-perfect").

- [ ] **Step 3: Add a manual "Check for Updates" menu item**

Wire it to call the updater plugin's check function and show a native dialog if an update is available (Tauri's dialog plugin, or the updater plugin's own built-in prompt if it has one — check current docs). Don't build a fully automated silent-background-update flow for this round — a manual, user-triggered check proves the mechanism works; automatic periodic checking can be added later without restructuring anything here.

- [ ] **Step 4: Verify what CAN be verified without a real release**

There is no published GitHub Release yet, so "Check for Updates" will correctly report "no update available" or a fetch error against the not-yet-existing manifest URL — that's expected, not a bug. What to actually verify: the app doesn't crash when the check fails/finds nothing, the public key is correctly embedded in the built config (`npm run tauri build` succeeds with the updater plugin active), and the private key file was generated and is NOT present anywhere under `desktop/` that would get committed (`git status` after this task should show no new key-shaped files).

- [ ] **Step 5: Document the release process**

Add a short `desktop/README.md` section (or a new `desktop/RELEASING.md`) explaining: how to bump the version, run `npm run tauri build`, sign the artifacts with the private key generated in Step 1, and upload the installer + generated `latest.json` to a GitHub Release for this repo. This is documentation, not automation — a GitHub Actions release workflow is a reasonable future addition but out of scope for this plan.

- [ ] **Step 6: Commit**

```bash
git add desktop/
git commit -m "Wire auto-update checking against GitHub Releases"
```

(Confirm the private signing key is genuinely not staged — check `git status` before committing.)
